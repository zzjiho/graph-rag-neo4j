# KG_P2_03 10-K Report (섹션 7)

> 강의: 프로젝트 3 - 기업 분석, 테슬라 10-K 보고서 기반 RAG (45~49강)

## 이 강의의 학습 목표

이 강의를 마치면 다음을 할 수 있어요.

1. 긴 보고서를 **문서 → 섹션 → 청크** 계층 그래프로 저장하고, 청크끼리 `NEXT`로 순서를 이을 수 있어요.
2. 섹션 노드를 왜 `(이름, 문서 id)` 조합으로 구분하는지 설명할 수 있어요.
3. 벡터 검색으로 찾은 청크에서 `NEXT*0..1`을 따라 **앞뒤 청크까지** 붙여 가져올 수 있어요.
4. 그래프에 남은 섹션 정보로 답변에 **출처**를 달고, 그 출처가 얼마나 정확한지 따져 볼 수 있어요.

읽기 전에 이 질문 하나를 머리에 두고 보면 좋아요. **"보고서를 그냥 청크로 잘라 벡터 DB에 넣는 것(classic RAG)과 비교하면, 그래프로 넣었을 때 뭐가 좋아질까?"**

## 한눈에 보기

**10-K**는 미국 상장사가 매년 내는 사업보고서예요. 목차가 양식으로 정해져 있어서, 어느 회사든 Item 1 Business(사업 개요), Item 1A Risk Factors(위험 요인)처럼 같은 이름의 섹션이 같은 순서로 나와요. 이번에는 테슬라 2024년 10-K(PDF 144쪽)를 써요.

강사가 미리 이 보고서를 **섹션 17개**로 나누고, 섹션마다 3,000자씩 잘라 **청크 253개**로 만들어 둔 파일(pkl)을 줘요. 이번 프로젝트는 이걸 그대로 그래프로 옮겨요.

```
(Document: 테슬라 2024 10-K)
   ├─HAS_SECTION→ (Section: Business)        ─CONTAINS→ 청크 1 ─NEXT→ 청크 2 ─NEXT→ … 청크 17
   ├─HAS_SECTION→ (Section: Risk Factors)    ─CONTAINS→ 청크 1 ─NEXT→ … 청크 27
   ├─HAS_SECTION→ (Section: 재무제표)          ─CONTAINS→ 청크 1 ─NEXT→ … 청크 112
   └─ … 섹션 17개, 청크 253개
```

- `HAS_SECTION`, `CONTAINS`는 **위아래**(어디에 속하나)예요.
- `NEXT`는 **옆으로**(몇 번째 다음인가)예요. 같은 섹션 안에서만 이어서, 다 넣으면 253 − 17 = 236개가 생겨요.

## 1. 섹션은 (이름, 문서 id)로 구분해요

```cypher
CREATE CONSTRAINT IF NOT EXISTS
FOR (s:Section) REQUIRE (s.name, s.document_id) IS UNIQUE
```

지금은 보고서가 한 권이라 섹션 이름 17개가 다 달라요. 그런데 내년에 2025년 10-K를 하나 더 넣으면 어떻게 될까요? 목차가 똑같으니 `Business`가 또 나와요.

| 섹션 구분 기준 | 2024년, 2025년 보고서를 같이 넣으면 |
|---|---|
| `name`만 | 두 해의 `Business`가 노드 하나로 합쳐져서, 청크가 뒤섞여요 |
| `(name, document_id)` | "2024년의 Business", "2025년의 Business"로 따로 생겨요 |

ETF의 섹터 노드는 여러 ETF가 **함께 가리키라고** 이름만으로 만들었어요. 반면 섹션은 **어느 한 보고서의 일부**라서, 소속 문서까지 붙여야 하나를 정확히 가리켜요.

> 강의는 `IS NODE KEY`로 쓰는데, 이건 Neo4j 유료(Enterprise) 기능이라 Docker Community 버전에서는 에러가 나요. `IS UNIQUE`로 바꾸면 돼요.

## 2. 청크를 저장하고 NEXT로 잇기

청크마다 이 순서로 넣어요.

```cypher
MATCH (s:Section {name: $section_name, document_id: $doc_id})
MERGE (c:Chunk {chunk_id: $chunk_id, content: $content, order: $order, ...})
WITH c, s
CALL db.create.setNodeVectorProperty(c, 'embedding', $embedding)   // 저장하면서 바로 임베딩
MERGE (s)-[:CONTAINS]->(c)
```
```cypher
MATCH (prev:Chunk {chunk_id: $prev_chunk_id})
MATCH (next:Chunk {chunk_id: $next_chunk_id})
MERGE (prev)-[:NEXT]->(next)
```

**왜 굳이 순서를 잇냐면**, 청크는 3,000자마다 기계적으로 잘려서 문장 중간에서 끊겨요. 실제로 Business 섹션의 13번과 14번 청크 경계는 이래요.

```
청크 13 끝:   ... paid parental leave, paid time off, company
청크 14 시작: (13번에서 끊긴 문장이 여기서 이어져요)
```

13번만 보면 문장이 끊겨 있어요. 그래서 나중에 13번을 찾았을 때 14번을 같이 붙여 줄 수 있도록 `NEXT`로 이어 두는 거예요.

알아 둘 점이 두 가지 있어요.
- **이 셀은 한 번만 실행해요.** `chunk_id`를 실행할 때마다 새로 만들어서(uuid), 다시 돌리면 MERGE가 새 노드로 보고 청크 253개가 통째로 한 벌 더 생겨요.
- **청크마다 OpenAI 임베딩을 한 번씩 불러요(253번).** 비용은 몇 원이에요.

## 3. 벡터로 찾고, 앞뒤 청크까지 붙이기

벡터 검색은 `Neo4jVector`로 해요. 여기서 핵심은 `retrieval_query`예요. 벡터 검색이 청크를 찾은 **다음에** 실행할 Cypher를 직접 넣는 옵션이에요.

```cypher
MATCH (c:Chunk {chunk_id: node.chunk_id})                 // 벡터 검색이 찾은 청크
OPTIONAL MATCH (c)<-[:CONTAINS]-(s:Section)                // 어느 섹션인지
OPTIONAL MATCH window = (prev:Chunk)-[:NEXT*0..1]->(c)-[:NEXT*0..1]->(next:Chunk)
WITH c, s, score, nodes(window) AS context_nodes
RETURN apoc.text.join([x IN context_nodes | x.content], '\n\n') AS text, score
```

`[:NEXT*0..1]`은 [Cypher 고급](../KG_P1_02_neo4j_cypher_advanced)에서 배운 가변 길이 경로예요. "0홉 또는 1홉"이라, 13번 청크를 찾으면 12번(앞) + 13번 + 14번(뒤)을 한 덩어리로 이어 붙여요. 0부터 시작하는 이유는, 섹션의 첫 청크처럼 앞 청크가 없어도 빠지지 않게 하려는 거예요.

**강의 결과**: "What recognition did Tesla receive in the 2024 American Opportunity Index?"로 k=5 검색을 했더니 **18개**가 돌아왔어요. 다섯 개를 찾으랬는데 왜 18개일까요?

가변 길이 경로는 맞는 길을 **전부** 돌려줘요. 그래서 13번 청크 하나에서 창이 네 가지로 나와요.

| 창 | 붙은 청크 |
|---|---|
| 0홉, 0홉 | [13] |
| 앞 1홉 | [12, 13] |
| 뒤 1홉 | [13, 14] |
| 앞뒤 1홉 | [12, 13, 14] |

그래서 노트북은 `remove_duplicates`로 같은 청크는 하나만 남겨요. 다만 어떤 창이 남는지는 순서에 따라 달라서, `[13]`만 남으면 애써 붙인 앞뒤가 사라질 수 있어요. 가장 긴 창을 골라 남기는 게 안전해요.

## 4. 출처를 단 RAG 체인

찾은 창들을 프롬프트에 넣고 `gpt-4.1`로 답을 받아요(LCEL 체인). 컨텍스트마다 섹션 정보가 붙어 있어서 답변 끝에 이런 출처가 달려요.

```
출처: Business 섹션(p.5) - 청크 순서 13
```

classic RAG는 "비슷한 텍스트 조각"만 돌려주지만, 그래프에는 **어느 섹션의 몇 번째 조각인지**가 남아 있어서 이런 출처를 달 수 있어요.

그런데 이 출처를 믿고 PDF 5쪽을 펼치면 답이 없어요. `p.5`는 청크가 있는 쪽이 아니라 **Business 섹션이 시작하는 쪽**이거든요. 실제 답은 PDF 14쪽에 있어요. 청크마다 정확한 쪽 번호를 넣어 두지 않았기 때문이에요. 출처를 정확히 하려면 청크를 만들 때 쪽 번호부터 챙겨야 해요.

## 5. 처음 질문으로: 그래프로 넣으면 뭐가 좋아질까?

| | classic RAG (청크만 저장) | 이번 방식 (계층 그래프) |
|---|---|---|
| 찾는 것 | 비슷한 청크 k개 | 비슷한 청크 + **앞뒤 청크** |
| 잘린 문장 | 끊긴 채로 LLM에게 가요 | 앞뒤를 붙여 문장이 이어져요 |
| 출처 | "어떤 조각"인지만 알아요 | 어느 보고서, 어느 섹션, 몇 번째인지 알아요 |
| 문맥 크기 조절 | 다시 자르고 다시 임베딩해야 해요 | 쿼리의 `*0..1`을 `*0..2`로 바꾸면 끝이에요 |

마지막 줄이 특히 좋아요. 청크를 겹치게 자르는(overlap) 방식은 청킹할 때 정해져서 바꾸려면 처음부터 다시 해야 하지만, `NEXT`로 이어 두면 **검색할 때마다** 문맥 크기를 고를 수 있어요.

## 6. 정리하며 기억할 것

- 목차가 있는 긴 문서는 **문서 → 섹션 → 청크** 계층으로 저장하면 출처와 소속이 남아요.
- 청크끼리 `NEXT`로 순서를 이어 두면, 검색할 때 `NEXT*0..1`로 앞뒤 문맥을 붙일 수 있어요.
- 가변 길이 경로는 맞는 길을 전부 돌려줘서 결과가 늘어나요. 중복 제거가 필요해요.
- 섹션처럼 "어느 한 문서의 일부"인 노드는 소속 문서 id까지 묶어서 구분해요.
- 출처의 쪽 번호는 청크를 만들 때 넣은 정보만큼만 정확해요.
- 이 방식은 사내 규정, 매뉴얼, 계약서처럼 목차가 있는 긴 문서 RAG에 그대로 쓸 수 있어요.
